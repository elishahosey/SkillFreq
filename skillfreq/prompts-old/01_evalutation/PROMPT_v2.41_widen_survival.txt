## target_lane

Use target_lane for roles primarily involving:

- data validation / reconciliation
- backend data processing
- APIs / integrations
- production debugging
- operational data workflows
- pipeline reliability
- reporting systems tied to operational workflows
- data quality tied to production/operational systems

A target_lane role should preserve backend/data mobility.

Do NOT classify generic Software Engineer, Python Developer, Java Developer, Full Stack, Systems Engineer, Platform Engineer, Admin, SRE, DevOps, or Infrastructure roles as target_lane unless the core role identity is clearly data engineering, ETL, SQL, integration, or backend data processing.

## secondary_lane

Use secondary_lane for adjacent technical roles involving:
- backend engineering with meaningful data/API/integration overlap
- software engineering with meaningful backend data workflow overlap

- BI/reporting engineering where SQL/data modeling/data quality is central
- application engineering where integrations, APIs, SQL, or production debugging are central
- database engineering where the work is development/data workflow oriented rather than DBA/admin

Use secondary_lane when:
- SQL, integrations, APIs, backend data processing, logs, troubleshooting, validation, or operational systems are materially important
BUT
- the role is not cleanly target_lane because engineering depth, title identity, tool stack, or platform risk is mixed

Secondary_lane roles can be strategically useful, but they need more caution than target_lane roles.

## bridge_lane

Use bridge_lane for strategic bridge roles involving:
- systems analyst
- application analyst
- production support analyst/engineer

- technical support engineer

- data quality analyst
- data operations analyst
- data integrity analyst
- reporting systems analyst

- interface analyst

- production data issues
- operational data workflows

Bridge_lane is acceptable when the role helps preserve SQL, systems thinking, debugging, integration, or operational data credibility.

Do NOT classify a role as bridge_lane if it is only generic customer support, help desk, nontechnical operations, generic business analyst work, training, customer success, or configuration-only implementation.

## survival_lane

Use survival_lane for technical fallback roles that are not strong enough to be target_lane, secondary_lane, or bridge_lane, but still preserve some technical credibility in a survival-market context.

Survival_lane roles may include:
- application support analyst / software support analyst roles where SQL, logs, data issues, API troubleshooting, or workflow troubleshooting appear but are not deeply central
- technical support engineer roles where troubleshooting application behavior, integrations, data delivery, logs, or API issues is visible
- reporting analyst / data analyst roles where SQL, reconciliation, data quality, or operational reporting exists but the role is more reporting/support than engineering
- data operations / data quality / data integrity roles where SQL or validation is present but the role is lighter-weight or more operational
- systems/application analyst roles where technical workflow troubleshooting exists but engineering depth is limited
- junior technical operations roles where SQL, data movement, logs, integrations, or production issue triage are real but secondary

Survival_lane is acceptable only when the role has at least one concrete technical overlap such as SQL, APIs, logs, data validation, data quality, reconciliation, XML/JSON/SFTP, application troubleshooting, production issue triage, or operational data workflows.

Do NOT use survival_lane for:
- fast food, retail, warehouse, call-center-only, or generic customer-service roles
- pure help desk / desktop support with no application/data/API/logs/workflow substance
- nontechnical administrative operations
- generic business analyst work with no SQL/data workflow substance
- customer success, training, onboarding, or implementation roles with no technical data/application troubleshooting
- configuration-only roles with no SQL/API/data/logs/debugging overlap

Survival_lane roles should usually be possible_fit or weak_fit.
Survival_lane roles should usually be manual_review only when the role has real technical overlap and could be used as a temporary fallback.
Survival_lane roles should be skip when the technical overlap is generic, weak, nontechnical, or likely to dilute backend/data mobility too much.

# FINAL RULES

- Be strict.
- Be decisive.
- Do not hedge.
- Do not repeat the entire job description.
- Do not include weak roles just to create volume.
- Do not upgrade roles based on theoretical learnability.
- Do not upgrade roles based on generic keyword overlap.
- Do not classify a role as good_fit unless it passes strict good_fit validation.
- Use the resume as the grounding source for what I can credibly claim in recruiter screening.
- Use SkillFreq as an evidence check to prevent inflated good_fit decisions.
- Prefer possible_fit over good_fit when the role has meaningful overlap but lacks enough core signals.
- Use weak_fit when recruiter-screen realism is genuinely low.
- Use bridge_lane deliberately for strategic bridge roles with real technical overlap.
- Use survival_lane deliberately for fallback technical survival roles with some SQL, data, application, troubleshooting, reporting-system, or operational workflow substance, but do not let generic support/admin work count as survival_lane.
- Do not use adjacent_lane.
