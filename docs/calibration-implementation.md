# Calibration implementation and review notes

This pass evolves the existing grader. The original 90-day export and its
configuration snapshot remain at `data/outputs/results-db-90-days.*`.
The new export is `data/outputs/results-db-90-days-calibrated.csv`, accompanied by
its own snapshot. [Measured results and posting examples](calibration-comparison.md)
are generated by `scripts/compare_calibration.py`.

## Problems confirmed

- All 8,692 baseline rows recorded a market `QueryCanceled` failure; every learning
  value was zero. Prevalence was already read once per run, not once per posting.
  Its SQL view unnecessarily reconstructed the clean-job × taxonomy population.
- The decision layer used the legacy alignment score and separate title/tool
  keyword checks, independently of the new fit score. It produced only two
  apply-now results and labeled high-fit jobs weak.
- Broad SQL profile evidence was not an authoritative record of product-specific
  proficiency. The atomic mapping was empty.
- Exact title phrases missed QA and test variants. Platform groups penalized
  technology use, while ecosystem checks blocked on single product mentions.
- Search metadata is absent from `clean_jobs`; its availability was not explicit
  in the grade. Some experience and equivalence wording also over-triggered gates.

## Database action and verification

The `CREATE OR REPLACE VIEW public.skill_prevalence` portion of
`db/job_skills.sql` was applied to the existing DB in a transaction. It now counts
canonical job-skill rows joined to their matching extraction scope/run and uses
all scoped jobs as denominator. The broad market population remains 127,801 jobs.
Zero-mention jobs and zero-mention technologies are retained. The read completed
in roughly 0.8 seconds after the change, versus the prior 30-second cancellation.

No extraction refresh or replacement of market rows was necessary. Filtered
dashboard slices still use `job_skill_prevalence_input`. They reflect current
clean-job attributes, while broad learning prevalence reflects the recorded
extraction snapshot. The grade records that population choice.

Grading-history and batch-import round trips were tested in rollback-only
transactions. A separate SQL fixture checks out-of-scope skills, stale run IDs,
zero mentions, and an empty denominator. All 53 tests passed with the optional
PostgreSQL tests enabled. Eight saved grades were replayed and matched their
exported lanes, scores, decisions and confidence. The final export's configuration
hash matches the current evaluator and profile.

## Representative review affected the calibration

The first new full run exposed network automation and VMware roles promoted by
the removal of broad platform-tool penalties. Reusable operational title identity
now overrides incidental Python/API/data overlap. Unknown titles require a
data-related identity before entering TARGET through the strong-content fallback.

Actual MDM postings used Hub Console, Match/Merge rules and provisioning tooling,
not just the abstract phrase “platform ownership.” Those controlled ownership
signals now explain ecosystem gates. The “Senior Informatica MDM Support Engineer”
posting also specified “Experience Required: 10 & Above”; an explicit configured
numeric experience pattern now captures it. Transferable ETL work merely using
Informatica remains eligible in regression fixtures.

## Assumptions and manual checks

- SQL, Python, Azure and Airflow atomic strengths reuse their existing exact
  profile evidence. SQL Server and PostgreSQL remain explicitly unconfirmed at
  zero until direct proficiency is supplied; no product knowledge was invented.
  Regression tests demonstrate that separate configured product experience is
  respected and does not grant MySQL knowledge.
- Search lane/review priority remain optional, with an explicit availability
  record. Missing search origin does not imply survival or bridge search.
- Secondary and bridge roles remain manual-review opportunities by default,
  even when their numerical fit band is good. This is an explicit career policy,
  not an unexplained weak-fit relabeling.
- Review unfamiliar ecosystems (e.g. vendor products outside the configured
  ecosystem groups), location/visa/clearance restrictions and unusual experience
  wording. This pass does not infer personal eligibility or add immigration,
  location or clearance policy without candidate configuration.
- Boundary/phrase matching is intentionally limited. Negation, mixed job duties,
  embedded employer boilerplate and badly scraped headings can need review.
  Confidence is not a statistical probability and a deterministic apply-now
  result still warrants reading the posting.

See [career-policy.md](career-policy.md) for concrete configuration edits, the
small rule vocabulary, and validation/rerun commands.
